# TUI Implementation Plan

> Use subagents to implement this plan task-by-task.

**Goal:** Add the third workspace package, `@swain/tui`, as an Ink-based interactive CLI for running the Swain agent loop with streaming model text, commands, file search, provider connection, usage display, and permission-mode cycling.

**Architecture:** Keep `@swain/core` headless and extend it only where the TUI needs public loop events and request options. Build `@swain/tui` as a thin interactive shell: it owns terminal state, command parsing, local config/credential storage, model selection, file search, approval UI, and user-question UI, while delegating model turns, tools, sessions, and permissions to `@swain/core` and `@swain/llms`.

**Tech Stack:** Bun, TypeScript ESM, Effect, Ink, React, Bun test runner, `@effect/platform-bun`, `@swain/core`, `@swain/llms`.

---

## Current Context / Assumptions

- Existing packages:
  - `@swain/llms`: provider-neutral streaming LLM API.
  - `@swain/core`: headless agent loop, tools, session persistence, permission modes.
- `core.runTurn()` currently collects a full model turn with `Stream.runCollect`; this prevents the TUI from rendering deltas as they arrive. The TUI should not duplicate the tool loop to work around that.
- `core.runTurn()` currently does not pass `generation` or `providerOptions` into `LLMClient.request`; model variants need that path.
- Session persistence currently lives under `.swain/sessions/<id>/`.
- Store API keys locally in a global Swain config file, defaulting to `${XDG_CONFIG_HOME:-~/.config}/swain/config.json`, with mode `0600`. Do not use `.env` as the primary auth source in the TUI. Provider facades may retain env fallback for non-TUI callers.
- Remove real provider API keys from any local `.env` used for interactive Swain sessions and run through the global TUI config instead. Keep `.env.example` as documentation for standalone package smoke tests and non-TUI callers that intentionally exercise provider env fallbacks. Update the `TODO` comment in `.env.example` to reflect this change.
- Initial supported providers in the TUI: Anthropic, OpenAI, DeepSeek, ZAI, OpenAI Codex. `packages/tui/src/models.ts` owns this static provider/model/variant list for this phase; `@swain/llms` remains the protocol/facade execution package, not the provider catalog.
- Permission mode cycling: `ask (default) -> auto -> plan -> ask`.
- `@<path/filename query>` search is a prompt-composition feature: selected files are inserted into the prompt as explicit path references, not silently read into context. There is no attach-contents command in this slice; reading remains a model/tool action.

## Key Decisions

- **Core event observer:** Refactor `runTurn()` to accept an optional `onEvent` observer. It emits provider events and tool lifecycle events while preserving the existing `Effect<void>` API and final session mutation semantics.
- **TUI runtime controller:** `@swain/tui` owns a `Controller` object that bridges Effect programs to React state. React components do not call provider APIs directly.
- **Commands are local:** Built-in `/` commands are parsed and executed in `@swain/tui`; only `/plan` sends a normal model prompt after switching permission mode to `plan`.
- **Provider config is typed and global:** Use Effect Schema for `${XDG_CONFIG_HOME:-~/.config}/swain/config.json`, with provider records containing non-secret settings plus API keys. Model/provider selection is entirely global for this phase; do not add named profiles, project-local overrides, or a separate credential package yet.
- **Connectable providers and runnable models are separate:** `/connect` shows every static provider from `models.ts` and lets the user store credentials/settings for each. `/model` shows only models whose provider is configured through TUI config or an accepted env fallback.
- **Reasoning controls are modeled as variants:** The TUI stores a selected variant id per provider/model. Provider-specific request patches live in `models.ts` for this phase and are lowered to `providerOptions` only when building the core request options.
- **Minimal Ink UI:** Build a durable REPL, transcript, status line, command overlays, approval modal, and user-question prompt. Do not add themes, telemetry, desktop integration, voice, tasks, MCP, or plugin UI in this phase.

## Task 2: Add Loop Event Observation To Core

**Objective:** Let UI consumers observe model deltas, tool calls, tool results, provider errors, and finish events without changing `runTurn()` behavior.

**Files:**
- Modify: `packages/core/src/agent.ts`
- Modify: `packages/core/src/index.ts`
- Modify: `packages/core/test/agent.test.ts`

**Design:**

Add a small event union:

```ts
export type AgentEvent =
  | { readonly type: "llm-event"; readonly event: LLMEvent }
  | { readonly type: "step-start"; readonly iteration: number }
  | { readonly type: "step-end"; readonly iteration: number; readonly reason: FinishReason; readonly usage?: Usage }
  | { readonly type: "tool-execution-start"; readonly name: string; readonly toolCallId: ToolCallId; readonly input: unknown }
  | { readonly type: "tool-execution-delta"; readonly name: string; readonly toolCallId: ToolCallId; readonly text: string }
  | { readonly type: "tool-execution-end"; readonly name: string; readonly toolCallId: ToolCallId; readonly isError: boolean }
  | { readonly type: "agent-error"; readonly source: "llm" | "agent" | "tool"; readonly message: string; readonly recoverable?: boolean }
```

Extend request options:

```ts
export interface RunTurnOptions {
  readonly maxIterations?: number
  readonly generation?: GenerationOptions
  readonly providerOptions?: ProviderOptions
  readonly onEvent?: (event: AgentEvent) => Effect.Effect<void>
}
```

Implementation constraints:

- `runTurn()` must call `options.onEvent` for each `LLMEvent` as it arrives.
- `runTurn()` must call `options.onEvent` for step start/end, tool execution start/end, and provider errors via `llm-event`.
- `agent-error` is an `AgentEvent`, emitted through the same observer stream. Use `recoverable: true` for nonfatal facts the UI should render while the turn continues, and `recoverable: false` immediately before the `runTurn()` Effect fails. Omit `recoverable` only when the caller cannot classify the failure.
- Do not duplicate nonfatal `LLMEvent` `provider-error` events as `agent-error`; forward those as `llm-event`. Use `agent-error` for failures outside the provider event stream: fatal `LLMError` failures, `AgentError` failures such as max iterations, and unexpected tool/runtime failures.
- `tool-execution-delta` is defined here as part of the union but is not emitted by this task. Its emitter and the underlying `Tool.call` progress channel land in Task 3 (`Bash` stdout streaming). Do not emit fake deltas for one-shot tools; the delta path is exercised end-to-end by Task 3, not synthesized here.
- It must still collect events for `LLMTurnSummary.fromEvents()`.
- It must append assistant messages and tool-result user messages exactly as `runTurn()` does today.
- It must pass `options.generation` and `options.providerOptions` into `LLMClient.request`.
- Existing callers that omit `onEvent` continue to receive the same `Effect<void>` behavior.

**Test first:**

Add a test in `packages/core/test/agent.test.ts` with a scripted LLM stream containing two `text-delta` events. Assert:

- `runTurn()` calls `onEvent` with both deltas in order.
- `runTurn()` emits `step-start` before streaming the provider request and `step-end` after the provider turn settles.
- A scripted tool call emits `tool-execution-start` before `callTool()` runs and `tool-execution-end` after the result is available.
- A scripted fatal `LLMError` emits one non-recoverable `agent-error` with `source: "llm"` before the `runTurn()` Effect fails.
- `session.messages` has the final assistant message only after the turn completes.
- existing `runTurn()` tests still pass unchanged.

## Task 3: Stream Tool Progress Through The Call Path

**Objective:** Give the tool contract a progress channel so long-running tools emit incremental output, and refactor `Bash` to stream stdout as `tool-execution-delta` events. This makes the delta member of `AgentEvent` a real, exercised event instead of a stub.

**Files:**
- Modify: `packages/core/src/tool.ts`
- Modify: `packages/core/src/agent.ts`
- Modify: `packages/core/src/tools/bash.ts`
- Modify: `packages/core/src/index.ts`
- Create: `packages/core/test/tools-bash.test.ts`

**Design:**

Add a per-call progress service, provided by `callTool`, not by the session runtime layer:

```ts
export interface ToolProgressValue {
  readonly emit: (delta: string) => Effect.Effect<void>
}

export class ToolProgress extends Context.Tag("@swain/core/ToolProgress")<
  ToolProgress,
  ToolProgressValue
>() {}
```

`callTool` gains an optional forwarder and always provides `ToolProgress` (default no-op) around `tool.call`:

```ts
export const callTool = (
  toolCall: ToolCall,
  onProgress?: (delta: string) => Effect.Effect<void>,
): Effect.Effect<ToolResultContent, never, ToolContext | ToolRegistry> => { ... }
// inside: tool.call(input).pipe(
//   Effect.provideService(ToolProgress, { emit: onProgress ?? (() => Effect.void) }))
```

Implementation constraints:

- **Scoping:** `ToolProgress` is provided per call inside `callTool` keyed to the active `toolCall`, not via the session `ToolContext` layer. The session runtime (`repl.ts`, TUI runtime) needs no new layer, and tools invoked through `callTool` with no observer see a no-op emitter. This is why existing Bash tests that call `callTool` keep passing unchanged.
- **Forwarding:** in `agent.ts`'s `loop`, when calling `callTool` for a tool call, pass `onProgress = (text) => onEvent?.({ type: "tool-execution-delta", name, toolCallId, text }) ?? Effect.void`. Deltas are emitted between the existing `tool-execution-start` and `tool-execution-end` events from Task 2.
- **Advisory only:** deltas are UI/observation output. They are never written to `session.messages`; the authoritative tool output remains the final `ToolResultContent`. A turn with no observer behaves exactly as today.
- **Requirements typing:** a streaming tool (`Bash`) adds `ToolProgress` to its inferred `ExtraRequirements` via `yield* ToolProgress`; one-shot tools do not reference it. `callTool` provides it regardless, so the erased `AnyTool` requirement is satisfied.

**Bash refactor:**

- Replace the `collectCapped(process.stdout, MAX_OUTPUT)` drain with a consumer that taps each decoded stdout chunk into `ToolProgress.emit` while folding the same capped `{ text, truncated }` result:
  - `process.stdout.pipe(Stream.decodeText(), Stream.tap((chunk) => progress.emit(chunk)), <capped fold>)`.
  - `Stream.tap` preserves ordering: each `emit` completes before the next chunk folds.
- Stream stdout only. `stderr` stays collected via `collectCapped` (carries stdout-shaped output).
- Cadence: emit per decoded stream chunk. No time/byte throttle in this slice; note throttling as a future refinement, not built now.
- Stop emitting once the cap is reached, consistent with `truncated`.
- The final `BashResult` shape (`stdout`/`stderr`/`exitCode`/`truncated`) is unchanged; existing behavior and timeout/abort handling are preserved.

**Tests (`packages/core/test/tools-bash.test.ts`):**

- A `printf 'a\nb\nc\n'`-style command run through `callTool` with an `onProgress` collector yields deltas whose concatenation equals the final `stdout`, in order, before the result resolves.
- Deltas are emitted before `tool-execution-end` when driven through `runTurn`/`onEvent` (assert ordering).
- A non-streaming tool invoked through `callTool` with no `onProgress` still succeeds (no-op emitter path).
- Output past `MAX_OUTPUT` still truncates the final result and stops further deltas.
- Existing Bash tests in `packages/core/test/permissions.test.ts` pass unchanged.

```bash
bun run --cwd packages/core typecheck
```

**Config shape:**

```ts
export interface TuiConfig {

    string,

      readonly apiKey?: string
```

Rules:

- Read/write through an injectable config file path so tests can use a temp path.

  - `~/.config/swain`, otherwise.

- Create the config directory with `0700` permissions where supported.
- Write `config.json` with `0600` permissions where supported.
- A failed config write (bad permissions, disk full, unwritable directory) must fail with a typed config error carrying a clear message; never partially write or silently drop the credential. The caller treats a failed save as not-saved so the user still has the env fallback and can retry.
- Keep project-local `.swain/sessions/<id>/` for conversation/session persistence. Credentials and user preferences are always global.
- Keep model/provider selection entirely global for now. Do not add named profiles or project-specific selection state.
- Never print full API keys. Display only provider configured/unconfigured state and a redacted suffix.
- Do not remove env fallback from `@swain/llms`; the TUI just prefers local config when constructing provider facades.
- Do not read or write project-local `.swain/config.json`.
- Update docs to tell users to remove real provider keys from local `.env` after connecting providers with `/connect`. Do not delete `.env.example`.
- TODO: Update `.env.example` in this task so its top comment documents the intended convention: provider env vars are for standalone package smoke tests and non-TUI callers, while the interactive TUI stores credentials in the global Swain config via `/connect`.

`models.ts` responsibilities:

- Define the initial static provider list by provider, including display name, required credential fields, env fallback names, supported models, and supported variants per model.
- Export `ProviderOption` and `ModelOption` types for controller/UI state; they should contain display metadata and ids, not provider credentials.
- Export catalog helpers:
  - `allProviders()`: every static provider the TUI knows how to configure.
  - `connectableProviders()`: every provider `/connect` should display; initially this is the same as `allProviders()`.
  - `configuredProviders(config, env)`: providers usable from stored TUI config or env fallback.
  - `availableModels(config, env)`: models shown by `/model`, filtered to configured providers and non-deprecated static models.
  - `resolveModelSelection(provider, modelId, variant?, config, env)`: validate the selected model/variant and return the `Model` plus request options for `core.runTurn()`.
- Build a `Model` from `(provider, modelId, config, env)`. Construct it through the `@swain/llms/providers` subpath facades (e.g. `Anthropic.configure(cfg).model(id)`, `OpenAI.configure(cfg).chat(id)`), mirroring the existing `packages/core/scripts/repl.ts` pattern. This is the one sanctioned facade-import site; the "no provider facades in React components" rule (see Key Decisions) does not apply to `models.ts`.
- Resolve `(provider, modelId, variant?)` into provider-specific `providerOptions`:
  - `openai-codex`: variants such as `low | medium | high` map to `{ openaiCodex: { reasoning: { effort } } }`.
  - `anthropic`: variants map to `providerOptions.anthropic.thinking` only where the existing protocol supports it.
  - OpenAI chat-compatible providers: expose no reasoning variants in this slice unless the protocol adds a supported field.
- Reject unknown variants for the selected model instead of silently downgrading them.
- Do not let React components import provider facades directly. Components call controller/model-registry helpers; request construction stays outside rendering.

`/connect` behavior:

- Validate only local catalog support and required field shape, then store the credential/settings.
- Do not send a live low-cost provider request while saving credentials.
- Do not add a standardized `@swain/llms` validation method until another caller needs real provider credential probing.

- Default path resolves to `~/.config/swain/config.json` with `HOME` set and no XDG override.
- `XDG_CONFIG_HOME` resolves to `$XDG_CONFIG_HOME/swain/config.json`.
- Saving config creates the global directory and file.
- Saved file mode is owner-readable/writable only where the platform exposes modes.
- Invalid JSON fails with a typed config error.
- A failed config write (e.g. unwritable directory) fails with a typed config error and leaves no partial file.
- API key redaction never returns the raw key.
- Static provider list includes Anthropic, OpenAI, DeepSeek, ZAI, and OpenAI Codex.

- `availableModels()` excludes providers with neither stored credentials nor env fallback.
- `availableModels()` includes a provider once its API key is saved in config.
- `resolveModelSelection()` rejects an unconfigured provider and an unknown variant.
- `resolveModelSelection()` on a configured provider returns a `Model` whose `provider`/`id` match the selection.
- `resolveModelSelection()` lowers a known variant to the expected `providerOptions` (e.g. `openai-codex` `high` → `{ openaiCodex: { reasoning: { effort: "high" } } }`; `anthropic` thinking variant → `providerOptions.anthropic.thinking`).

## Task 6: Implement File Search

**Objective:** Support `@<path/filename query>` suggestions in the prompt input.

**Files:**
- Create: `packages/tui/src/fs.ts`
- Create: `packages/tui/test/fs.test.ts`

**Behavior:**

- Detect the active file-search token only when the cursor is after a token starting with `@`.
- Search relative to the session working directory by default.
- If the token path starts with `../`, normalize it against the session working directory and search from that parent/outside directory.
- File search may list files outside the session working directory; `@../...` does not require approval just to populate browser suggestions.
- Reading or writing a selected outside-working-directory file still goes through the normal permission rules.
- Prefer exact prefix matches, then substring matches.
- Ignore `.git`, `node_modules`, `dist`, `.swain`, and hidden lock/cache folders.
- Return paths relative to the working directory, including `../` prefixes for matches outside it.
- On selection, replace only the active token with `@relative/path` or `@../relative/path`.

**Implementation:**

- Use Bun filesystem APIs for the first slice; keep the search bounded.
- Limit results to 20.
- Do not read file contents.
- Do not shell out to `rg` from the input component on every keypress.

**Tests:**

- Detects `@src/ag` in `please inspect @src/ag`.
- Detects `@../other` and searches outside the working directory without approval.
- Does not detect email-like text.
- Filters ignored directories.
- Ranks prefix before substring.
- Replaces the active token without changing the rest of the prompt.
- In `ask` mode, outside-working-directory search does not request approval for listing suggestions.

## Task 7: Build The Controller Runtime

**Objective:** Bridge UI actions to Effect programs, core sessions, provider models, local config, and streaming agent events.

**Files:**
- Create: `packages/tui/src/controller.ts`
- Create: `packages/tui/src/runtime.ts`
- Create: `packages/tui/src/usage.ts`
- Create: `packages/tui/test/controller.test.ts`

**Controller state:**

```ts
export interface TuiState {
  readonly session: SessionState
  readonly permissionMode: PermissionMode
  readonly activeModel: { readonly provider: string; readonly modelId: string; readonly variant?: string }
  readonly connectableProviders: ReadonlyArray<ProviderOption>
  readonly availableModels: ReadonlyArray<ModelOption>
  readonly running: boolean
}
```

`TuiState` is controller state, not React render state. Do not store transcript rows, draft assistant text, draft reasoning text, command output rows, or other display projections here. Components own those with local React state and derive completed conversation rows from `session.messages` when rendering or resuming.

**Controller actions:**

- `submitPrompt(text: string)`
- `executeCommand(result: CommandParseResult)`
- `cyclePermissionMode()`

**Streaming rules:**

- Pass `onEvent` to `runTurn()` and forward each `AgentEvent` to the UI subscriber immediately; do not wait for the whole turn to complete before exposing deltas.

- Completed model-visible history remains authoritative in `session.messages`; the UI transcript is a render projection that may include non-model-visible rows such as provider errors, tool progress, command output, approvals, and interruptions.
- Persist the session after a successful turn using `saveSession()`.
- On interruption, stop the stream and leave already-rendered draft text visible as interrupted output; do not append it to session history unless core completed the turn.

## Risks And Tradeoffs

- **Streaming correctness:** The TUI requirement exposes a real gap in `core.runTurn()`. Fixing core is safer than duplicating the loop in the TUI.
- **Variant semantics:** Reasoning controls are provider-specific. The first slice should expose only configured model variants and reject unsupported values, instead of inventing fake behavior.
- **Credential storage:** Global `~/.config/swain/config.json` avoids leaking API keys into per-project workspaces, but it is still not an OS keychain. It satisfies "stored locally" for this phase; a future credential package can replace it.
- **Ink testing:** Use `ink-testing-library` for deterministic render/input tests (`lastFrame`, `frames`, and `stdin.write`) with fixed terminal dimensions and injected services. Keep parser/controller/highlight tests pure, and reserve Ink tests for component composition, focus routing, key handling, and rendered output.
- **Tool progress contract:** Streaming tool output adds a `ToolProgress` channel to core's tool contract, provided per-call by `callTool` (not the session layer) so one-shot tools and observer-less turns are unaffected. Progress deltas are advisory and never persisted to `session.messages`; the final `ToolResultContent` stays authoritative. Per-chunk emit cadence is chosen for simplicity; throttling is deferred until it proves necessary.
- **Session resume model mismatch:** Persisted sessions store provider/model strings, but `core.loadSession()` requires a live `Model`. The TUI must rehydrate through `models.ts` and fail clearly if provider credentials are missing.

## Post-implementation changes

Behavioral changes made after the initial slice, recorded here so the spec stays the source of truth.

### Inline Edit diffs

Task 9 originally rendered a pending Edit's diff inside the floating permission overlay, where a long diff could be clipped off-screen. The diff now renders **inline on its tool-call row in the transcript** instead:

- **Pending edit:** while the approval prompt is up, the suspended Edit's diff (from `PermissionRequest.diff`) is attached to its still-running draft row and rendered inline, so it scrolls with the conversation and is never clipped. The permission prompt itself is now compact — tool, summary, and the Yes/No picker only; the diff is no longer drawn in the overlay.
- **Applied edit:** a completed Edit keeps its diff inline, sourced from the persisted tool result (`diffs[0].text`), so the change stays visible in history.
- **Rendering (`Diff.tsx`):** `parseDiff` turns the unified diff (as produced by `createPatch`) into displayable rows, dropping the file-header preamble and tracking per-hunk line numbers. `DiffView` renders a faint line-number gutter, green additions / red deletions, and an `+A -B` change summary. The full diff renders — unchanged context is already collapsed by the diff format and `@swain/core` caps pathological diffs at 400 lines — so no row cap is applied in the TUI.
- **Scrolling during approval:** the main input handler is inactive while the approval prompt owns the keys, so a dedicated handler keeps the transcript scrollable (mouse wheel plus Page Up/Down) while the prompt still owns Up/Down/Enter for the choice list. Wheel parsing is shared through `mouse.ts` `wheelScroll`.
